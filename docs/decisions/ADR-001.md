# ADR-001: Use a Modular Monolith for Release 1

- Status: Accepted
- Date: 2026-07-29

## Context

Release 1 serves one agency and must make Lead changes, Timeline, Audit, open
Follow-up ownership, and Notifications consistent. The product boundaries are
still evolving, and there is no demonstrated need for independent service
scaling.

## Decision

Build one deployable application organized into explicit business modules with
one transactional database. Keep domain and application boundaries independent
of the chosen framework. Modules communicate through public application
interfaces and in-process domain events; they do not write one another's
persistence models.

## Consequences

- Business actions can commit their required effects atomically.
- Deployment, local development, and testing remain straightforward.
- Module discipline must be enforced in code review and dependency checks.
- Failure or scaling isolation is at application level in Release 1.
- A module may be extracted later only with measured operational justification
  and an explicit consistency design.

## Rejected Alternatives

- Microservices: premature operational and distributed-transaction complexity.
- Unstructured layered monolith: insufficient protection of business
  boundaries.
- Serverless function per endpoint: risks duplicating state rules and makes
  transaction ownership unclear at this stage.
